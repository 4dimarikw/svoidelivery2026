**SEC-01. Подмена ссылки сброса пароля**

Маршрут `POST /forgot-password` генерирует ссылку через стандартный `ResetPassword::resetUrl()`, использующий URL текущего запроса. В [bootstrap/app.php](D:/WebProject/svoidelivery2026/bootstrap/app.php:14) не настроен список доверенных Host; переопределения генерации ссылки на фиксированный доверенный origin также не найдено.

В тесте создаётся только синтетический пользователь. Запрос с origin `http://audit.invalid` проходит через HTTP kernel приложения. `Notification::fake()` перехватывает уведомление; проверяется только домен `actionUrl`, без публикации токена. Ожидается `localhost`, фактически `audit.invalid`. Дополнительно реальный локальный HTTP-сервер принимает `Host: audit.invalid` для `/login` с кодом 200.

Последствие: если боевой reverse proxy пропускает произвольный Host и пользователь перейдёт по подменённой ссылке из настоящего письма, токен сброса может попасть атакующему. Перехват реального токена и захват аккаунта не выполнялись. Эксплуатируемость на публичном домене зависит от конфигурации веб-сервера.

Исправление: разрешить только известные домены на proxy и в Laravel; генерировать ссылки сброса и подтверждения почты от явно заданного доверенного HTTPS origin. Одного `APP_URL` недостаточно, если генерация продолжает брать Host текущего запроса. Методика: [OWASP — Host Header Injection](https://owasp.org/www-project-web-security-testing-guide/stable/4-Web_Application_Security_Testing/07-Input_Validation_Testing/17-Testing_for_Host_Header_Injection).

**SEC-02. Скрытое меню не ограничивает доступ к настройкам**

В [MoonShineLayout.php](D:/WebProject/svoidelivery2026/app/MoonShine/Layouts/MoonShineLayout.php:116) раздел «Система» скрыт от Manager через `canSee`. Однако [EventLoggingSettingsPage::save()](D:/WebProject/svoidelivery2026/app/MoonShine/Pages/EventLoggingSettingsPage.php:70) не проверяет полномочия пользователя.

Тесты с настоящей ролью Manager, созданной штатным сидером прав, подтверждают:

- GET страницы `event-logging-settings-page` возвращает 200 вместо отказа.
- POST маршрута `moonshine.method` с `pageUri=event-logging-settings-page` и `method=save` меняет настройки.
- При отсутствии полей переключателей в `disabled_event_types` записываются отключаемые типы событий.

Последствие: менеджер может отключить сохранение событий приложения в `event_logs`. Это не означает отключение всех файловых журналов или мониторинга сервера.

Исправление: серверная проверка роли/permission при открытии страницы и непосредственно при выполнении каждого изменяющего метода. Проверить аналогичные скрытые страницы импорта, VK и планировщика: их обход в рамках этого аудита отдельно не воспроизводился. Предсказуемость префикса админки не должна быть частью модели безопасности.

**SEC-03. Сохранение через GET обходит защиту CSRF для изменяющего действия**

Маршрут `moonshine.method` зарегистрирован для GET, HEAD, POST, PUT, PATCH, DELETE и OPTIONS. Контроллер пакета вызывает метод, отмеченный `AsyncMethod`, без ограничения HTTP-метода. В [EventLoggingSettingsPage.php](D:/WebProject/svoidelivery2026/app/MoonShine/Pages/EventLoggingSettingsPage.php:69) дополнительного ограничения нет.

Воспроизведение в тестовой БД с авторизованным администратором: GET `/<admin-prefix>/method/event-logging-settings-page?method=save`. После запроса проверяется таблица настроек: список отключённых типов действительно изменён.

Laravel не требует CSRF-токен для GET. Cookie SameSite=Lax обычно отправляется при межсайтовой навигации верхнего уровня. Поэтому переход авторизованного администратора по подготовленной ссылке может изменить настройки. Межсайтовая цепочка в отдельном браузерном origin не выполнялась; изменяющий GET и отсутствие требования CSRF для этого метода подтверждены кодом и тестом.

Исправление: разрешить изменяющие async-методы только через POST/PATCH/DELETE с CSRF; для GET/HEAD возвращать отказ до любых изменений. Ограничение должно действовать на сервере. Нужны аналогичные проверки всех остальных async-методов.

**SEC-04. Массив в email вызывает ошибки сервера**

При наличии корректной сессии и CSRF-токена отправка JSON с `"email": ["audit"]` вызывает 500:

| Маршрут | Ошибка |
|---|---|
| POST /login | TypeError |
| POST /register | Array to string conversion |
| POST /forgot-password | Array to string conversion |
| POST /reset-password | Array to string conversion |

Причина: [FortifyServiceProvider.php:49](D:/WebProject/svoidelivery2026/app/Providers/FortifyServiceProvider.php:49) передаёт вход в `Str::lower()` до проверки типа; [строка 134](D:/WebProject/svoidelivery2026/app/Providers/FortifyServiceProvider.php:134) приводит массив к строке. Исключение возникает ещё при вычислении ключа rate limiter, поэтому эти запросы не проходят нормальный учёт попыток этим лимитером. Нагрузочная атака не выполнялась; отказ в обслуживании не объявляется доказанным.

Ошибка сохраняется и при `app.debug=false` — это отдельно проверено. При включённом debug текущий HTTP-сервер дополнительно возвращает имя исключения, трассировку и пути файлов.

Исправление: обрабатывать нестроковые идентификаторы до строковых функций; возвращать контролируемую ошибку валидации, сохраняя общий IP-лимит для некорректных запросов. Запретить массивы недостаточно только на уровне HTML-формы.

**SEC-05. Перебор существующих email**

Для двух синтетических адресов `POST /forgot-password` с `Accept: application/json` различается по статусу: существующий → 200, отсутствующий → 422. Реальные письма в этом тесте не отправляются.

Последствие: внешний клиент может определять наличие учётной записи и использовать результат для целевого подбора паролей или фишинга. Имеющиеся лимитеры уменьшают скорость, но не устраняют различие ответов.

Исправление: одинаковый статус и нейтральный текст независимо от существования адреса, например «Если аккаунт существует, инструкция будет отправлена». Также контролировать различие времени ответа. Рекомендация: [OWASP — Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

**Наблюдения по конфигурации**

- Текущий сайт использует `APP_ENV=local`, `APP_DEBUG=true`; в ответах 404, 419 и 500 доступны трассировки, зарегистрированы маршруты Debugbar. Для разработки это ожидаемо. На публичном сервере это был бы отдельный риск раскрытия информации. Доступ ко всей истории Debugbar не исследовался.
- В ответе `/login` отсутствуют CSP, X-Frame-Options, X-Content-Type-Options и Referrer-Policy. Пакет CSP установлен, но его наличие само по себе заголовок не добавляет. Для production нужна политика, совместимая с Alpine, Telegram и CAPTCHA, и защита от нежелательного встраивания страниц. Само отсутствие CSP не доказывает XSS.
- Сессионная cookie имеет HttpOnly и SameSite=Lax; Secure отсутствует на локальном HTTP. Отсутствие HttpOnly у XSRF-TOKEN нормально. TLS, HSTS и фактические cookie на production надо проверять отдельно.
- Лимитер публичного входа привязан к паре email+IP; отдельного совокупного лимита на IP в нём нет. Это оставляет возможность распределять попытки между разными email. Массовый подбор не выполнялся; рекомендуется дополнительный IP-лимит и мониторинг.

**Проверка в браузере**

На основном локальном адресе открыты каталог, вход, регистрация и восстановление пароля. Вход с неверными данными/SQL-строкой отклонён; email без `@` не проходит браузерную валидацию регистрации и восстановления. CAPTCHA не решалась и не обходилась. XSS-строка в `q` дала пустую выдачу без исполнения маркера.

Для форм после входа временно запущена копия на `127.0.0.1:8001`, использующая только `svoidelivery2026_test`, отдельные сессии и перехват исходящих уведомлений/задач. Синтетический пользователь вошёл; в профиле `javascript:` отклонён сервером. Сохранённые SVG/IMG-маркеры после перезагрузки остались текстом. Аналогично проверен адрес: HTML отобразился буквально в списке. В корзине маркеры подставились в поля как текст; неверный телефон заблокировал отправку формы. Число заказов осталось 0. Выполнен выход; временный сервер остановлен. Синтетический аккаунт, его профиль, адрес, корзина и тестовый товар удалены из тестовой БД.

Смена пароля через UI не выполнялась: её серверные сценарии проверены автоматическими тестами. Административные права проверены через HTTP kernel в тестах, а не входом в реальные административные аккаунты. Боевые заказы не создавались, реальные пароли/права/настройки не менялись.
