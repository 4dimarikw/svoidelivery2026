# Исправления и повторная проверка SvoiDelivery — 12 сентября 2026

Согласованный план реализован в приложении. `vendor` и миграции не менялись, права ролей не расширялись. Боевой сервер не изменялся. Локальный сервер на порту 8000 перезапущен с `APP_ENV=production`, `APP_DEBUG=false`.

## Исправленные дефекты

| Дефект | Исправление и подтверждение |
| --- | --- |
| Подмена Host и адреса письма | Production принимает только точный hostname из `APP_URL` и явно перечисленные `SECURITY_TRUSTED_HOSTS`; неизвестный Host — 400. Отдельный генератор создаёт reset/verify ссылки от `APP_URL`; общая генерация ссылок админки не меняется. Проверены подпись, подмена домена и истечение срока verify-ссылки. |
| Обход административных прав | Middleware проверяет доступ до MethodController. Логирование, импорт, VK-настройки, планировщик, очистка журнала и тестовый заказ — только superuser. Общие настройки доступны Manager. Изменяющие действия ресурсов проверяют policy фактического объекта. Для заказов добавлена policy, использующая существующие записи прав. |
| Изменения через GET | Изменяющие async-действия используют POST с CSRF; перемещение — PATCH. Кнопки, включая формы подтверждения, обновлены. GET/HEAD отклоняются без выполнения действий. Поиск и загрузка компонентов через GET сохранены. Маршрут запуска планировщика защищён отдельно. |
| Нестроковый email вызывает 500 | Безопасные ограниченные ключи лимитеров и проверка типа до обработки Fortify. На четырёх маршрутах email-массив возвращает 422; некорректные запросы учитываются лимитерами. Сохраняется лимит входа 5/min на email+IP, добавлен 30/min на IP. Секреты не возвращаются в old input. |
| Раскрытие существования аккаунта при восстановлении | Корректный email получает одинаковые JSON 200 и HTML redirect/status при существующем, отсутствующем аккаунте и внутреннем ограничении повторной отправки. Сообщение: «Если аккаунт существует, инструкция будет отправлена». Валидация и общие 429 сохранены. |

Дополнительно закрыт вызов CRUD-метода без ресурса в URL: MoonShine способен найти такую страницу глобально, что раньше позволяло пропустить проверку объекта. Отсутствующий либо несовместимый ресурс теперь возвращает 404 до вызова метода. Отвязка Telegram ограничена текущим администратором; подставленный идентификатор отклоняется.

## Очередь и заголовки

- Reset-уведомление реализует `ShouldQueue` и `ShouldBeEncrypted`, использует настроенную очередь (`database` в текущем `.env`). HTTP-запрос не выполняет MailChannel/SMTP. Задание имеет 3 попытки, задержки 30/120 секунд, timeout 30 секунд.
- Проверена запись зашифрованного payload в таблицу jobs, обработка database job с перехваченным MailChannel, release после искусственного сбоя и успешная повторная обработка Worker. Наборы SafeLogging и FailedJobPrivacy прошли. SMTP наружу не выполнялся.
- Добавлены `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, базовая CSP `base-uri 'self'; object-src 'none'`.
- Для админки действуют CSP `frame-ancestors 'none'` и `X-Frame-Options: DENY`.
- Ограничения скриптов и встраивания публичных страниц пока Report-Only: это диагностика, не полноценная блокировка XSS. Alpine продолжает работать. Проверка реальных Telegram Mini App и SmartCaptcha на публичном домене остаётся отдельным этапом.
- Secure-cookie по умолчанию зависит от HTTPS в `APP_URL`; HSTS выдаётся только для production HTTPS. Локальный HTTP работает без них.

## Браузер

Проверки выполнены в отдельном локальном процессе на порту 8001 и БД `svoidelivery2026_test`, с синтетическими аккаунтами, реальным CSRF и перехватом Mail/Notification/Queue; непредусмотренные HTTP-вызовы запрещены. Проверены:

- Неверный пароль: ошибка формы без внутренних данных; успешный вход ведёт в профиль.
- Восстановление для существующего и отсутствующего email: одинаковое нейтральное сообщение.
- Профиль: `javascript:`-ссылка отклоняется; XSS-маркер сохраняется и после перезагрузки остаётся текстом.
- Адреса: синтетический адрес сохраняется, XSS-маркер отображается текстом.
- Корзина: добавление тестового товара, увеличение количества 1 → 2, пересчёт 100 → 200; значения профиля и комментария экранированы.
- Manager: прямое открытие настроек логирования даёт 403; общие настройки открываются и сохраняются с CSRF, результат сохраняется после reload.
- Superuser: доступ к журналу, открытие и отмена модального подтверждения очистки. POST и CSRF этого подтверждения дополнительно проверены HTML-тестом. Прямую навигацию браузера к изменяющему endpoint заблокировал браузерный инструмент; отказ GET проверен HTTP kernel-тестами.

Тестовый браузерный процесс остановлен, временные router/fixture-файлы удалены. Следующий полный PHPUnit-прогон пересоздал тестовую БД. Боевые заказы, реальные пароли и внешние сообщения не создавались и не менялись. Смена пароля и успешный checkout проверены автоматическими тестами; финальные действия этих форм в браузере не выполнялись.

## Настройка и границы проверки

Новые параметры описаны в `.env.example`: `SECURITY_TRUSTED_HOSTS` — дополнительные точные имена хостов через запятую; `SECURITY_TRUSTED_PROXIES` — явные IP/CIDR доверенных proxy; `LOGIN_THROTTLE_PER_IP=30`; `SECURITY_HSTS_MAX_AGE=31536000`. Без proxy список оставляют пустым. Поддомены автоматически не разрешаются. Для отдельного административного домена его явно добавляют в trusted hosts; `APP_URL` остаётся каноническим публичным адресом.

Текущий канонический адрес — `http://localhost:8000`. Обращение к `127.0.0.1` с таким Host не разрешено автоматически: это другое имя, которое при необходимости включают в дополнительный список.

При последующей выкладке необходимо проверить реальный worker database-очереди и SMTP-доставку, перезапустить долгоживущие процессы с новым кодом/окружением, проверить внешний HTTPS, reverse proxy, Secure-cookie и HSTS. Пример команды worker: `php artisan queue:work database --tries=3 --timeout=30`; её эксплуатационный запуск на боевом сервере в этот этап не входит. Таймаут worker должен оставаться меньше `retry_after` выбранной очереди.

Не выполнялись полноценные нагрузочные испытания, request smuggling на реальном proxy, реальная рассылка Telegram/VK, передача XML на FTP и полный ручной аудит всех загрузок и зависимостей. Локальный регрессионный набор прошёл; это не гарантия отсутствия любых возможных уязвимостей или проверки всех внешних интеграций.
