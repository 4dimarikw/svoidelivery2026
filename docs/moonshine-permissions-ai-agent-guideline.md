# Guideline для AI-агента: система MoonShine permissions

## 1. Назначение и границы

Используйте это руководство для построения системы административных прав по схеме **роль → модель → действие** в другом приложении Laravel 12 / MoonShine 4. Результат — управляемая через админку матрица прав с проверкой через Laravel Gate, строгой валидацией и кешем на один жизненный цикл контейнера.

Примеры сверены с исходниками этого проекта: PHP 8.4, Laravel 12.69.1, MoonShine 4.19.1; необязательный пакет импорта — `moonshine/import-export` 2.1.0. Это базовая версия примеров, а не обещание совместимости со всеми версиями пакетов. Перед переносом проверьте `composer.lock` целевого приложения и реальные сигнатуры установленного кода. Пакет Laravel Content CMS для этой системы не требуется.

Система не задаёт права отдельных записей, владельцев, арендаторов или состояний сущностей. Несколько ресурсов одной модели используют одну матрицу. Новые роли, особые действия и изменение существующей бизнес-матрицы требуют отдельного требования пользователя.

Выполняйте инструкции целевого проекта и пользователя в пределах действующих инструкций агента. Не переносите автоматически роль Manager, её разрешения и перечень разделов SuperUser из приложения-примера. Не редактируйте `vendor` и выполненные миграции.

## 2. Обследование перед реализацией

До изменения кода:

1. Прочитайте инструкции проекта, выполните `git status --short`, сохраните несвязанные изменения.
2. Установите версии PHP, Laravel, MoonShine и расширений по `composer.json`, `composer.lock` и установленным исходникам.
3. Найдите административный guard, модель пользователя, связь с ролью и способ определения SuperUser. В примере guard — `moonshine`, а `isSuperUser()` сравнивает ID роли с `MoonshineUserRole::DEFAULT_ROLE_ID`, не её название.
4. Соберите зарегистрированные `ModelResource`, их модели, `$withPolicy`, policies, правила авторизации конфигуратора и ограничения меню, включая родительские группы.
5. Найдите все точки записи прав: форма, импорт, сидеры, команды, SQL-операции. Отдельно перечислите пользовательские страницы, методы и handlers с изменением данных.
6. Проверьте схему таблицы, длину поля модели, внешние ключи, индексы, дубли и существующий формат JSON. Для работы с данными используйте согласованное окружение.
7. Определите тестовую БД, имеющиеся проверки доступа и способ просмотра обычных и модальных форм.

Зафиксируйте исходную матрицу и видимость меню в тестах до рефакторинга. Если бизнес-правила отсутствуют, уточните их у пользователя; для новых несогласованных разрешений используйте отказ.

## 3. Контракт доступа и компоненты

### 3.1. Восемь действий

Источником допустимых ключей служит `MoonShine\Support\Enums\Ability`. Русские подписи храните централизованно и проверяйте соответствие enum тестом.

| Ключ JSON / метод policy | Enum | Подпись формы |
|---|---|---|
| `viewAny` | `VIEW_ANY` | Просмотр списка |
| `view` | `VIEW` | Просмотр записи |
| `create` | `CREATE` | Создание |
| `update` | `UPDATE` | Редактирование |
| `delete` | `DELETE` | Удаление |
| `restore` | `RESTORE` | Восстановление |
| `massDelete` | `MASS_DELETE` | Массовое удаление |
| `forceDelete` | `FORCE_DELETE` | Окончательное удаление |

Вызов общего policy сначала разрешает действие SuperUser. Для остальных отсутствие роли, записи разрешений или ключа означает `false`. Действия независимы: разрешение `update` само по себе не разрешает `viewAny`. Наличие права восстановления не добавляет модели механизм SoftDeletes.

### 3.2. Разделение ответственности

| Компонент | Ответственность |
|---|---|
| `MoonshinePermission` | Данные пары роли и модели, JSON cast, события сброса кеша |
| `PermissionCache` | Чтение прав с кешированием в текущем scope |
| Трейт `MoonshinePermissionPolicy` | Восемь методов и общий алгоритм решения |
| Policy конкретной модели | Подключение трейта и регистрация в Gate |
| `PermissionModels` | Каталог зарегистрированных моделей и метаданные ограничений меню |
| `PermissionData` | Общие правила, подписи и нормализация входных данных |
| Ресурс / FormPage | Редактор матрицы и подключение общей валидации |
| Обработчик импорта, если нужен | Проверка каждой строки и очистка временного файла |

Имена можно адаптировать к соглашениям проекта. Сохраните единый источник правил для формы и импорта, а также единый источник метаданных для меню и пояснений.

## 4. Хранение и миграции

Используйте таблицу `moonshine_permissions`: `id`, `moonshine_user_role_id`, `model` (FQCN модели, строка длиной 255 в примере), `permissions` (JSON), timestamps. Внешний ключ роли должен соответствовать фактической таблице ролей. В примере удаление и изменение ключа роли каскадные; при переносе сохраните согласованную политику целевого проекта.

В модели объявите `belongsTo` роли, разрешённые для заполнения поля и cast `permissions => array`. Сохраняйте значения действий настоящими JSON boolean. Переименование PHP-класса модели требует переноса её FQCN в существующих разрешениях: morph map сам по себе это поле не обновляет.

Уникальность обеспечивает БД, даже если валидация формы уже проверяет дубли:

```php
use Illuminate\Database\Schema\Blueprint;
use Illuminate\Support\Facades\Schema;

Schema::table('moonshine_permissions', function (Blueprint $table): void {
    $table->unique(
        ['moonshine_user_role_id', 'model'],
        'moonshine_permissions_role_model_unique',
    );
});
```

Для новой таблицы добавьте индекс при создании. Для существующей создайте отдельную миграцию. До изменения схемы выполните группировку по роли и модели с `HAVING COUNT(*) > 1`; для каждой конфликтующей пары получите отсортированные ID. При наличии дублей выбросьте исключение со всеми парами и ID. Не удаляйте записи, не объединяйте разрешения и не выбирайте победителя автоматически.

Откат этой дополнительной миграции удаляет уникальный индекс, сохраняя данные и внешний ключ. Учтите MySQL: составной индекс может заменить прежний индекс внешнего ключа. Перед его удалением восстановите отдельный индекс роли, если он отсутствует. Проверьте `up/down` на том же типе СУБД, который используется в проекте; тест SQLite не подтверждает поведение MySQL.

Предварительная проверка дублей не устраняет гонку с параллельной записью. Во время внедрения приостановите изменение матрицы; окончательную защиту обеспечивает уникальный индекс.

## 5. Policies и Gate

Для каждой модели ресурса с `$withPolicy = true` создайте policy с восемью публичными методами из таблицы. Каждый метод передаёт FQCN модели и соответствующий `Ability` общему алгоритму. Пример фрагмента трейта:

```php
use App\MoonShine\Support\PermissionCache;
use Illuminate\Database\Eloquent\Model;
use MoonShine\Laravel\Models\MoonshineUser;
use MoonShine\Support\Enums\Ability;

public function update(MoonshineUser $user, Model $model): bool
{
    return $this->isCan($user, $model::class, Ability::UPDATE);
}

protected function isCan(MoonshineUser $user, string $model, Ability $ability): bool
{
    if ($user->isSuperUser()) {
        return true;
    }

    $roleId = $user->moonshineUserRole?->id;
    if ($roleId === null) {
        return false;
    }

    $permissions = app(PermissionCache::class)->get($roleId, $model);

    return (bool) ($permissions[$ability->value] ?? false);
}
```

Для остальных семи методов используйте ту же сигнатуру с соответствующим enum. Если административный пользователь имеет другой класс, адаптируйте тип и получение роли. Cast к `bool` здесь опирается на валидированные данные; он не заменяет входную валидацию и проверку старых записей.

В установленном MoonShine 4.19.1 `ModelResource::isCan()` передаёт экземпляр модели даже для `create`, `viewAny`, `massDelete`; для остальных действий использует текущую запись. При прямом вызове Gate придерживайтесь того же контракта. Обычный Laravel-вызов `Gate::allows('create', ModelClass::class)` не передаст второй аргумент, требуемый этим трейтом.

Policy подключает общий трейт. Если автоматическое обнаружение Laravel не подтверждено тестом, зарегистрируйте соответствие явно в `boot()` провайдера. Пример для модели `App\Models\Product` целевого приложения:

```php
use App\Models\Product;
use App\Policies\ProductPolicy;
use Illuminate\Support\Facades\Gate;
use MoonShine\Laravel\MoonShineAuth;

// В boot() провайдера:
Gate::policy(Product::class, ProductPolicy::class);

// В обработчике действия, после подключения аутентификации:
$user = MoonShineAuth::getGuard()->user();
abort_if($user === null, 401);
Gate::forUser($user)->authorize('create', new Product());
```

Для пакетных моделей namespace policy обычно отличается от namespace модели — используйте явное соответствие. Добавьте policy и для самой модели разрешений. Доступ к изменению матрицы выдавайте только согласованным администраторам: он позволяет изменять права других ролей.

Обход SuperUser находится внутри policy. Если Gate не находит policy и нет другого разрешающего механизма, обход не выполняется — доступ запрещён и SuperUser. Правила конфигуратора MoonShine могут отказать ещё до Gate; не заменяйте эту схему глобальным `Gate::before`, расширяющим обход на всё приложение.

Аутентификация обязательна отдельно. В установленном `ModelResource::isCan()` отсутствие пользователя возвращает `true`; защиту от гостя обеспечивает middleware. Проверяйте реальные маршруты, а не только вызовы policy.

Для произвольных страниц, методов, импортов и handlers проверьте серверную авторизацию независимо от видимости кнопок. Сопоставьте действие одному из восьми разрешений либо существующему ограничению SuperUser. Проверяйте именно модель/запись, которую обработчик затем изменит. Не считайте `$withPolicy` универсальной защитой всех пользовательских endpoints.

## 6. Кеш и его сброс

Зарегистрируйте сервис через `scoped` в `register()` провайдера:

```php
use App\MoonShine\Support\PermissionCache;

$this->app->scoped(PermissionCache::class);
```

Контракт сервиса: `get(int $roleId, string $model): ?array` и `forget(int $roleId, string $model): void`. Внутренний ключ включает обе части. Кешируйте также отсутствие записи — используйте `array_key_exists`, поскольку `isset` не различает отсутствующий ключ и сохранённый `null`:

```php
// Внутри PermissionCache; MoonshinePermission импортирован из App\MoonShine\Models.
private array $permissions = [];

public function get(int $roleId, string $model): ?array
{
    $key = $roleId.':'.$model;
    if (! array_key_exists($key, $this->permissions)) {
        $this->permissions[$key] = MoonshinePermission::query()
            ->where('moonshine_user_role_id', $roleId)
            ->where('model', $model)
            ->first()?->permissions;
    }

    return $this->permissions[$key];
}

public function forget(int $roleId, string $model): void
{
    unset($this->permissions[$roleId.':'.$model]);
}
```

В `booted()` модели разрешений подключите `saved` и `deleted`. В обработчике получите **текущий** `app(PermissionCache::class)` и удалите ключи текущей и исходной пары. Исходную пару берите через `getRawOriginal()` до синхронизации оригинальных атрибутов. Это закрывает создание после закешированного отсутствия, изменение флагов, перенос разрешения между ролями/моделями и удаление.

Не захватывайте экземпляр scoped-сервиса заранее в статическом callback или singleton. Не используйте статический массив прав, глобальный бессрочный кеш или специальное отключение кеша для тестов.

Границы механизма:

- `query()->update/delete`, `DB::table`, тихое сохранение и каскадное удаление БД обходят события модели. Если такая операция необходима, явно сбросьте затронутые пары; следующий корректно начатый scope также перечитает данные.
- Laravel сбрасывает scoped-экземпляры в управляемых им жизненных циклах, в том числе Octane/queue worker. Собственный долгий цикл команды не создаёт новый scope на каждой итерации автоматически; установите границы обработки и проверяйте сброс отдельно.
- Изменение из другого процесса не рассылает сигнал текущему scope. Свежие права гарантируются при новом scope, а не мгновенно внутри уже выполняющегося запроса.
- События Eloquent сами по себе не обеспечивают согласованность кеша после отката транзакции. Если права читаются после записи внутри транзакции, при rollback сбросьте затронутые ключи и добавьте отдельный тест. В примере специальный механизм rollback не реализован.

## 7. Общая валидация

Каталог моделей стройте из `moonshine()->getResources()`, оставляя `ModelResource`. Ключ — `$resource->getModel()::class`, подпись — название модели и ресурса. Используйте одни и те же ключи каталога в Select и `Rule::in`. Не принимайте произвольный FQCN из запроса.

Если одну модель обслуживают несколько ресурсов, объедините их пояснения, чтобы ограничения одного ресурса не затёрли ограничения другого. В приложении-примере варианты индексируются FQCN; при переносе такой конфигурации её надо обработать явно.

Общий валидатор должен проверять:

| Поле | Правила |
|---|---|
| `moonshine_user_role_id` | Обязательное целое, существующая роль |
| `model` | Обязательная строка, длина не больше колонки БД, присутствует в каталоге |
| Пара роли и модели | Уникальна с исключением текущей сохранённой записи |
| `permissions` | Поле присутствует, массив, только ключи `Ability` |
| `permissions.*` | Обязательное булево значение для каждого переданного ключа |

Опорные правила Laravel:

```php
use Illuminate\Validation\Rule;
use MoonShine\Support\Enums\Ability;

$abilities = array_column(Ability::cases(), 'value');
$safeRoleId = filter_var($inputRoleId, FILTER_VALIDATE_INT) ?: 0;

$pairRule = Rule::unique('moonshine_permissions', 'model')
    ->where('moonshine_user_role_id', $safeRoleId)
    ->ignore($persistedItemId);

$permissionsRules = [
    'permissions' => ['present', 'array:'.implode(',', $abilities)],
    'permissions.*' => ['required', 'boolean'],
];
```

`$persistedItemId` берите из загруженной сервером существующей записи, для создания передавайте `null`. Не передавайте в `ignore()` необработанный ID запроса или CSV. Роль для SQL-условия приводите к проверяемому скаляру, сохраняя отдельную валидацию исходного поля: массив вместо ID должен давать ошибку данных, а не SQL-исключение.

Принимайте только `true`, `false`, `0`, `1`, `"0"`, `"1"`. Строки `"true"`, `"false"`, `"yes"`, число `2`, `null`, массивы и неизвестные действия отклоняйте. После проверки нормализуйте допустимые значения к `bool`. Не приводите произвольный ввод к `bool` до проверки: например, строка `"false"` превратится в `true`.

Отсутствующий ключ действия означает запрет; все восемь ключей во входе не обязательны. Пустая карта допустима, отсутствующее поле `permissions` и `null` — нет. Для новой формы задавайте все восемь значений `false` явно.

Форма использует общие `rules()`, импорт вызывает общую проверку до сохранения. Нормализацию можно дополнительно запускать в Eloquent `saving`, но она не заменяет валидатор. Команды и другие входы также должны валидировать непроверенные данные; сидеры формируют типизированную согласованную матрицу.

## 8. Форма и меню

Форма содержит связь роли, поиск по разрешённому каталогу моделей и фиксированный JSON-объект переключателей. Свободное добавление и переименование JSON-ключей исключите. Фрагмент поля для MoonShine 4:

```php
use App\MoonShine\Support\PermissionData;
use MoonShine\UI\Fields\Json;
use MoonShine\UI\Fields\Switcher;

Json::make('Разрешённые действия', 'permissions')
    ->object()
    ->fields(array_map(
        static fn (string $key, string $label): Switcher =>
            Switcher::make($label, $key)->default(false),
        array_keys(PermissionData::LABELS),
        array_values(PermissionData::LABELS),
    ))
    ->default(array_fill_keys(array_keys(PermissionData::LABELS), false));
```

`PermissionData::LABELS` содержит ровно восемь пар из раздела 3. Проверьте реальную отправку выключенных переключателей и JSON после сохранения. Редактирование должно показывать сохранённые значения, а отсутствующие старые ключи — запрет.

В общей метаинформации перечислите ограничения меню целевого приложения, включая наследуемые от групп. Меню использует её в `canSee`, форма — в подписи выбранной модели или рядом с полем:

- «Меню только для SuperUser»: разрешение модели не открывает этот раздел меню.
- «Матрица не управляет доступом: без policy»: ресурс не включает `$withPolicy`.

Сохраните исходную видимость меню. Не открывайте разделы автоматически из-за включённых флагов и не включайте policies для всех ресурсов без проверки прежнего поведения. Метаданные видимости не являются серверной авторизацией; реальные запреты страниц и методов проверяются отдельно.

В примере ограничения групп и отдельных пунктов собраны в `PermissionModels::SUPERUSER_MENU`. Это проектная конфигурация, а не стандартный перечень MoonShine.

## 9. Импорт и экспорт, если они нужны

Не устанавливайте пакет импорта только ради матрицы. Если импорт существует, сохраните его контракт. В примере колонки: `id`, `moonshine_user_role_id`, `model`, `permissions`; CSV использует `;`, экспорт возвращает те же поля.

В `beforeImported()` проверяйте уже заполненную модель общим валидатором до `save()`:

```php
use App\MoonShine\Support\PermissionData;

public function beforeImported(mixed $item): mixed
{
    $item->permissions = app(PermissionData::class)->validate($item);

    return $item;
}
```

При обновлении исключайте из уникальности только найденную существующую запись. Ошибочная строка не должна создавать запись или менять старые права. Обрабатывайте ошибку валидации в принятом формате интерфейса; не показывайте уведомление об успешном завершении после исключения.

В `moonshine/import-export` 2.1.0 базовый `process()` удаляет файл после успешного чтения строк. Исключение из `beforeImported()` пропускает эту очистку. Для синхронного импорта используйте наследника с той же сигнатурой; ключевой фрагмент его `process()`:

```php
try {
    return parent::process($path, $resource, false, $delimiter, $notifyUsers);
} finally {
    if ($deleteAfter && is_file($path)) {
        unlink($path);
    }
}
```

Передача `false` родителю оставляет очистку одному владельцу. Подключите наследника в ресурсе; при замене существующего handler сохраните alias маршрута (в примере `import-handler`), disk, delimiter и прочие настройки. Если `deleteAfter` выключен, обработчик сохраняет файл.

Для нового проекта выбирайте приватное временное хранилище. В приложении-примере исторически используется `public/imports`; исправление удаляет файл в `finally`, но не делает его приватным во время обработки. `finally` покрывает нормальное завершение и исключения при доступной файловой системе; аварийное завершение процесса и отказ удаления требуют отдельной уборки и диагностики.

**Очередь требует отдельной реализации.** В указанной версии `ImportHandlerJob` вызывает базовый `ImportHandler::process()` напрямую, поэтому одного наследника недостаточно. Если нужен queued import, подключите собственный job с нужным обработчиком, определите судьбу файла при повторных попытках и окончательном отказе, протестируйте эти сценарии. Текущий пример проверяет синхронный путь.

Базовый импорт сохраняет строки по одной: при ошибке поздней строки ранее обработанные строки могут остаться в БД. Не заявляйте атомарность всего файла. Если пользователь требует «всё или ничего», добавьте транзакцию и тест отката всего набора, учитывая сброс кеша после rollback.

## 10. Сидеры и внедрение

Сидер использует согласованную матрицу с настоящими bool и `updateOrCreate` по паре роли и модели. Повторный запуск не создаёт дубли, но может перезаписать ручные изменения матрицы — поэтому он не должен безусловно выполняться при каждом деплое.

Manager в приложении-примере может редактировать контент без создания и удаления его структуры. Это пример бизнес-решения, а не универсальный набор прав. Не выдавайте все действия каждой зарегистрированной модели ради удобства начальной настройки.

Порядок внедрения:

1. На тестовой БД проверьте новую установку и обновление существующей схемы с данными, включая миграцию `up/down`.
2. Подготовьте резервную копию и приостановите изменение прав на время изменения схемы.
3. Выполните миграцию до включения новой функциональности. При дублях остановите внедрение, передайте пары и ID ответственному за данные; после ручного исправления повторите миграцию.
4. Примените только согласованный сидер, если он требуется; проверьте доступ SuperUser и обычной роли.
5. Перезапустите долгоживущие процессы согласно процедуре проекта, проверьте формы, меню и защищённые endpoints.

Не мигрируйте рабочую БД при разработке, не используйте `migrate:fresh` для внедрения. При откате учитывайте совместимость кода и схемы; удаление уникального индекса не должно удалять разрешения.

## 11. Обязательные проверки

Проверяйте поведение через Gate, HTTP и настоящий обработчик импорта, а не только отдельные вспомогательные методы.

| Область | Сценарии |
|---|---|
| Gate | Для каждого из восьми действий: SuperUser, разрешение и запрет роли, отсутствие записи и ключа; отдельно отсутствие роли |
| Аутентификация | Гостевой запрос к защищённому маршруту отклонён; используется административный guard |
| Кеш | Повторное чтение существующей и отсутствующей записи без повторного SQL; независимость ролей и моделей |
| Инвалидация | Создание после кеширования отсутствия, изменение флагов, роли и модели, удаление; старый и новый ключи перечитываются |
| Scope | Новый экземпляр после `forgetScopedInstances()` видит изменение БД; для долгих процессов дополнительно проверить реальный используемый lifecycle |
| Уникальность | Дубль отклоняется БД и формой; редактирование своей записи допустимо |
| Миграция | Дубли останавливают `up` с парами и ID до изменения схемы; данные неизменны; `down` сохраняет строки и FK |
| Валидация | Неизвестная/слишком длинная модель, неизвестная роль, массив вместо ID, неизвестное действие, неверное значение, `null` и отсутствующее поле |
| Нормализация | Все шесть допустимых представлений boolean сохраняются настоящими bool; пропущенный ключ запрещён |
| Policies | Обход всех зарегистрированных `$withPolicy = true`: Gate находит policy, все восемь методов вызываемы |
| Форма | Создание и редактирование, все восемь переключателей, сохранение включённых и выключенных значений, ошибки и пояснения |
| Меню / endpoints | Прежние наборы видимых пунктов для обычной роли и SuperUser; прямые запросы к запрещённым действиям отклоняются |
| Импорт | Валидное создание/обновление, дубли и неверные данные, неизменность ошибочной записи; удаление upload при успехе/исключении, сохранение при выключенном `deleteAfter` |

Пример проверки покрытия policies внутри загруженного Laravel-теста:

```php
use Illuminate\Support\Facades\Gate;
use MoonShine\Laravel\Resources\ModelResource;
use MoonShine\Support\Enums\Ability;

$count = 0;
foreach (moonshine()->getResources() as $resource) {
    if (! $resource instanceof ModelResource || ! $resource->isWithPolicy()) {
        continue;
    }
    $policy = Gate::getPolicyFor($resource->getModel());
    self::assertNotNull($policy, $resource::class);
    foreach (Ability::cases() as $ability) {
        self::assertTrue(is_callable([$policy, $ability->value]), $resource::class);
    }
    $count++;
}
self::assertGreaterThan(0, $count);
```

Сверьте набор ключей `PermissionData::LABELS` с `Ability::cases()`. Запустите новые тесты и существующие проверки безопасности, CMS-разрешений и MoonShine целевого проекта. Перед тестами с `RefreshDatabase`/`DatabaseMigrations` проверьте фактическое тестовое подключение: они изменяют БД. Факт успешного тестирования примера не подтверждает работоспособность переноса.

В браузере откройте обычную и модальную формы создания и редактирования на широком и узком экране (например, 1280 и 390 px). Проверьте подписи, поиск модели, пояснения, ошибки, переключение и сохранение значений, прокрутку и отсутствие горизонтального переполнения. Если проверка недоступна, укажите это в отчёте явно.

## 14. Критерии завершения

- Для всех согласованных ресурсов Gate применяет матрицу и отказ по умолчанию; SuperUser проходит существующие правила обхода.
- БД исключает дубли, миграция сообщает конфликты без изменения данных, откат сохраняет записи и FK.
- Кеш охватывает найденные и отсутствующие записи, сбрасывается при изменениях и не переносится между scope.
- Форма и импорт принимают одинаковые данные; JSON содержит bool; новая запись запрещает все действия.
- Меню сохраняет прежнюю видимость, форма объясняет ограничения, пользовательские endpoints имеют серверные проверки.
- Импорт, если подключён, не сохраняет ошибочную запись и очищает временный файл на проверенных путях успеха и ошибки.
- Тесты и визуальные проверки выполнены с зафиксированным результатом; непроверенные сценарии и ограничения перечислены явно.
- Подготовлен порядок внедрения, рабочая БД не изменялась при разработке, несвязанные изменения сохранены.
