# Правила категоризации в конфиге

Источник правил — config/category_matching.php, список rules. Снимок перенесён
из локальной БД 12 сентября 2026: 23 активных правила. Категории, их флаги,
маркеры импорта и fallback остаются в прежних таблицах/настройках.

Поля каждой записи: slug, type, match_when, value, priority, is_active.
Типы: alcohol (advent/no_abv/style/default), contains, accessory_title.
Для alcohol/style и обоих остальных типов необходимо непустое value.
Для alcohol/advent, no_abv, default value равно null; у остальных типов
match_when равно null. priority — целое 0–65535, is_active — boolean.
При равном priority сохраняется порядок списка, включая порядок regex-альтернатив.

Правила проверяет catalog:validate-registry до импорта. Отключённые записи
сохраняются и проверяются по структуре и существованию целевой категории,
но не участвуют в сопоставлении и проверке конфликтов активных правил.
Категории существующих товаров повторный импорт не переназначает.

## Переход существующего окружения

1. Остановить запуски импорта и дождаться завершения текущего импорта.
2. Сделать резервную копию category_match_rules со схемой, ID и временными
   метками штатным инструментом БД; проверить возможность восстановления.
3. Прочитать все записи через LEFT JOIN с categories, ORDER BY priority, id.
   Сверить с конфигом slug, type, match_when, value, priority, is_active,
   включая отключённые правила. Отличия перенести в конфиг и проверить в Git.
4. Развернуть код, выполнить composer dump-autoload и php artisan config:cache.
   Выполнить php artisan catalog:validate-registry.
5. Выполнить php artisan migrate --force. Новая миграция повторно сверяет
   таблицу с конфигом и отказывается удалять её при любом расхождении.
   Не обходить отказ ручным DROP: сначала устранить расхождение.
6. Перезапустить queue workers и другие долгоживущие процессы штатным способом.
   Проверить catalog:validate-registry и возобновить расписание импорта.

Кеш категорий имеет новый ключ; правила не хранятся в общем кеше.
После последующих изменений конфига также обновлять config cache и workers.

## Откат

Откат новой миграции на текущем коде восстанавливает таблицу и записи из
текущего конфига, включая отключённые и порядок. До отката не менять конфиг.
Старый код разворачивать после восстановления таблицы, затем пересобрать
автозагрузку/конфигурацию и перезапустить процессы.
Для точного восстановления прежних ID и временных меток нужна резервная копия.

Исходная миграция сохранена. Чистая установка проходит исходную схему и новую
миграцию перехода. При изменении начального набора правил в будущем необходимо
отдельно проверить совместимость чистой установки с историческим наполнением;
защитную сверку перехода существующих баз отключать нельзя.

Рабочая локальная БД при разработке этого изменения не мигрируется.
