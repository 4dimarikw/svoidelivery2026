# Формы и ресурсы MoonShine

## Как тип меняет форму

| Метод / данные типа | Результат |
| --- | --- |
| key(), label() | Выбор типа блока в административной форме |
| blockFields() | Поля JSON content при редактировании блока |
| blockRules() | Проверка content при редактировании блока |
| itemGroups() | Допустимые группы; поля и правила JSON элемента |
| mediaCollections(), fileCollections() | Поля загрузки изображений и файлов блока |
| ContentItemGroup.mediaCollections | Поля изображений элемента |

Например, чтобы добавить подзаголовок, добавьте `$this->text('Подзаголовок', 'subtitle')` в blockFields и `'subtitle' => ['nullable', 'string', 'max:255']` в blockRules. В Blade используйте `$block->content['subtitle'] ?? ''`. Общую FormPage менять не требуется.

Поля content появляются после первого сохранения. Создание проверяет основные поля; типизированные правила применяются при редактировании. Не добавляйте `content.` в ключи правил типа/группы. Required в правилах отвечает за серверную проверку; соответствующее поле можно дополнительно отметить `->required()` для UI.

## Пять ресурсов

- SiteSectionResource — разделы, маршруты, якоря, связанные блоки.
- SiteMenuResource — меню и связанные пункты.
- SiteMenuItemResource — цели ссылок, родители, перестановка и перенос веток.
- ContentBlockResource — выбор типа, JSON, media и элементы.
- ContentBlockItemResource — группа элемента, JSON и изображения.

## Генерация и владение кодом (2.0)

```shell
php artisan content-cms:publish-moonshine --dry-run
php artisan content-cms:publish-moonshine
```

Команда создаёт 22 файла в `app/ContentCms/MoonShine`: ресурсы, страницы, UI-trait, пять policies и `ContentCmsMoonShineServiceProvider`. Добавьте `App\ContentCms\MoonShine\ContentCmsMoonShineServiceProvider::class` в `bootstrap/providers.php`. Он регистрирует ресурсы и policies ровно один раз. Namespace отделён от `App\MoonShine`; не подключайте одновременно вторую регистрацию этих классов.

Исполняемых ресурсов пакета и `register_resources` больше нет. Локальные классы без `final` принадлежат приложению: редактируйте формы, фильтры и действия там. Обновление Composer их не перезаписывает. Для сравнения с новой версией каркаса используйте `--output=build/cms-comparison`. Генератор не поддерживает `--force`, отказывается от любого конфликта до записи и не следует ссылкам назначения. Не используйте vendor как постоянное место правок.

## Права и служебные поля

Во всех ресурсах включено `protected bool $withPolicy = true`. Стандартные policies разрешают операции только пользователю с публичным `isSuperUser() === true`; без этого метода доступ закрыт. Не отключайте policies для добавления редакторов. Измените конкретные методы локальных policies и определите прикладные разрешения, например в `ContentBlockPolicy`:

```php
public function update(\Illuminate\Contracts\Auth\Authenticatable $user, \ContentCms\Models\ContentBlock $item): bool
{
    return $this->allowed($user)
        || \Illuminate\Support\Facades\Gate::forUser($user)->allows('edit-site-content');
}
```

`edit-site-content` — пример разрешения, которое приложение должно определить само. Отдельно настройте `viewAny`, `view`, `create`, `delete` и `massDelete`; разрешение обновления не открывает остальные операции. Для ограничений по разделам проверяйте переданный `$item`. При переносе ветки проверяйте также целевое меню и родителя, если проектные права зависят от них.

Скрытие кнопки или `readonly()` не защищает прямой запрос. Например, для неизменяемого служебного ключа блока добавьте проверку в observer приложения и зарегистрируйте его для пакетной модели:

```php
public function saving(\ContentCms\Models\ContentBlock $block): void
{
    if ($block->exists && $block->isDirty('key')) {
        throw \Illuminate\Validation\ValidationException::withMessages([
            'key' => 'Этот служебный ключ изменять нельзя.',
        ]);
    }
}
```

Это пример проектного ограничения, а не правило всех CMS-блоков. Проверьте прямые запросы изменения, включая inline-поля и PATCH-действия. Методам меню нужна серверная проверка UPDATE; отказ возвращается явным JSON 403, поскольку обработчик MoonShine преобразует выброшенные HTTP-исключения в 500.

## Поведение форм

Сохраняйте `stopFilteringEmpty()` у JSON-полей, чтобы можно было очистить вложенные значения и списки. Связь «Элементы блока» отображается только для типов с группами. Для URL с локальными путями и якорями используйте `Text` и правило `ContentCms\Rules\SafeContentUrl`; поле `Url` браузера ограничивает ввод абсолютными ссылками.

Раздел без маршрута — общая область: `route_name = null`, fragment пустой. Такой раздел исключается из целей меню. В форме якорь отключается при пустом маршруте; модель повторяет нормализацию на сервере.

Настройки сайта, layout, пользователи, guard, роли и прикладные страницы остаются в приложении. Встроенного import/export нет.

## Проверка

Проверяйте обе стадии создания, фактическое сохранение JSON, очистку списков, обязательные поля и media после повторного открытия формы. Проверяйте права прямыми HTTP-запросами, сохранность дерева и удаление файлов. Для генератора используйте отдельное приложение и временную БД.
