# Laravel Content CMS

Пакет `dimarik/laravel-content-cms` (namespace `ContentCms`) предоставляет пять моделей и генератор пяти локальных ресурсов MoonShine: разделы, меню, пункты меню, блоки и элементы. Целевая платформа — Laravel 12, PHP 8.4, MoonShine 4 и Spatie Media Library 11.

Типы, шаблоны, маршруты, иконки, настройки и бизнес-логика принадлежат принимающему приложению. Новая установка использует одну начальную миграцию пяти таблиц с nullable-маршрутом общих разделов; общую таблицу media устанавливает Spatie. Новый тип обычно не требует миграции: данные находятся в JSON `content`.

Админка генерируется командой `content-cms:publish-moonshine` в `app/ContentCms/MoonShine`. Подключается только сгенерированный provider приложения. Команда не перезаписывает файлы: для сравнения используйте `--output=build/cms-comparison`. Локальные ресурсы, страницы и policies принадлежат приложению; настройка `register_resources` удалена.

Общие разделы имеют `route_name = null`, пустой fragment и не имеют URL. Загружайте их через `LoadPublishedSectionByKey::handle('header')`; в выборку страницы они автоматически не входят. Не создавайте на них цели меню.

## Как работать

Перед изменением изучите установленную версию пакета, `config/content-cms.php`, нужный тип и его потребителей в приложении. Исходники в vendor можно читать для уточнения API, но постоянные исправления пакета вносите в его исходный репозиторий.

- Для нового типа или изменения схемы читайте [примеры типов](references/block-types.md).
- Для полей форм, валидации, media и административных страниц читайте [интеграцию MoonShine](references/moonshine.md).

Создавайте прикладной класс на основе `AbstractContentBlockType`, регистрируйте его в `content-cms.types`, затем добавляйте явное сопоставление с публичным шаблоном в приложении. Каталог иконок и правила для него также определяет приложение.

Для нового поля существующего типа обновите соответствующие поля и правила, публичный вывод и тесты. Предусмотрите отсутствие значения в старом JSON через `??`/`data_get`. Обязательность нового поля означает, что при следующем редактировании старой записи редактор должен его заполнить. Массовое заполнение существующих данных — отдельная часть задачи, а не побочный эффект установки типа.

Для новой группы добавьте `ContentItemGroup` со стабильным ключом; ключ массива `itemGroups()` должен совпадать с `$group->key`. Не переименовывайте существующие ключи групп, типов и коллекций без отдельного переноса данных. Разные типы могут иметь одинаковые ключи групп, но общий список групп в форме создания объединяет их; используйте различимые ключи, если названия или назначение различаются.

## Инварианты

- Тип существующего блока и группа элемента неизменяемы. Для смены создайте новую запись и перенесите данные в рамках задачи.
- Ключ раздела уникален; пара маршрут/якорь также уникальна. Ключ блока уникален в разделе, элемента — в паре блок/группа, пункта — в меню.
- Блок и элемент создаются в два этапа: сначала основные поля, затем содержимое в форме редактирования. Правила содержимого проверяются на втором этапе. Для подготовки черновика снимите активность при создании; автоматической проверки полноты перед публичной выборкой нет.
- Проверки `blockRules()` и правил групп обслуживают формы MoonShine. При программном сохранении JSON вызывающий код самостоятельно выполняет валидацию; observers защищают структурные инварианты.
- Изображения и файлы храните через именованные media collections, а не путями в JSON. Удаляйте модели через Eloquent для событий и очистки media; rollback схемы не очищает файлы.
- Пункт меню имеет ровно одну цель. Порядок хранится в scoped Nested Set, не в sort_order. Переносите ветку между меню через `MoveSiteMenuItemBranch`, не меняйте границы прямым SQL.
- URL проверяйте `ContentCms\Rules\SafeContentUrl` и разрешайте через `ContentCms\Support\SafeContentUrl`. Допустимы HTTP/HTTPS, локальные пути и якоря; обратный слеш запрещён.

## Публичный вывод и проверка

В контроллере используйте `LoadPublishedSections::handle($routeName)` и `BuildMenu::handle($menuKey)`. Разделы содержат `publishedBlocks`, у блоков — `publishedItems`; media загружены заранее. Неизвестные типы исключаются из публикации. В шаблоне используйте разрешённую карту views и экранированный вывод, не выполняйте новые запросы к БД.

Проверяйте регистрацию типа, создание и редактирование, обязательные поля, media, неактивный контент и старый JSON. Тесты запускайте в изолированной БД с временным media-диском. Для изменений ядра выполните тесты пакета, Pint и Composer validation. Не запускайте установочный сидер для перезаписи редакторского контента.

Skill не подразумевает разрешения на изменение других приложений, production-данных, публикацию или отправку коммитов. Выполняйте действия в пределах текущего запроса пользователя.
